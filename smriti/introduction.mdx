Smriti (स्मृति — Sanskrit for *"that which is remembered"*) is a zero-infrastructure, local-first memory layer for AI agents. It stores everything your agent knows and experiences in one portable SQLite file, giving you persistent, inspectable, bi-temporal memory with no Postgres, Neo4j, Redis, Docker, or cloud account required. Whether you're building a personal assistant, a coding agent, or a multi-turn chatbot, Smriti handles the memory so you can focus on the logic.

## Two modes

Smriti offers two operating modes so you can trade write-time cost against retrieval precision. Choose the mode that fits your infrastructure constraints and quality requirements.

<Tabs>
  <Tab title="Lite mode (laghu)">
    **Lite mode** — also aliased as `laghu` (लघु, Sanskrit for *"light"*) — ingests conversations as raw episodes and indexes them for four-channel hybrid retrieval. No LLM call is made at write time, which means:

    - Fully **offline**: no API keys, no network required
    - Near-zero write cost regardless of conversation volume
    - Strong recall from BM25 + vector + entity + temporal fusion
    - Best for privacy-sensitive deployments, CI pipelines, and constrained environments

    ```python
    from smriti import Smriti, HashEmbedder

    mem = Smriti(path="memory.db", embedder=HashEmbedder())
    # mode defaults to "lite" when no llm is provided
    ```

    <Note>
      Lite mode stores the full conversation transcript and retrieves it via all four channels. It won't extract structured facts like "user lives in Bengaluru," but it will surface the relevant episodes when you query for that information.
    </Note>
  </Tab>
  <Tab title="Full mode (purna)">
    **Full mode** — also aliased as `purna` (पूर्ण, Sanskrit for *"complete"*) — adds LLM-based fact extraction and temporal supersession on top of everything lite mode provides. Each session ingestion makes one extraction call to your configured LLM, which means:

    - Structured facts are extracted and stored with validity windows
    - Conflicting facts (e.g. a new home city) automatically supersede old ones
    - Both raw episodes **and** extracted facts are available at retrieval time
    - Works with Ollama, OpenAI, vLLM, LM Studio, Groq, DeepSeek, and OpenRouter

    ```python
    from smriti import Smriti, LLM, OllamaEmbedder

    mem = Smriti(
        path="memory.db",
        embedder=OllamaEmbedder("nomic-embed-text"),
        llm=LLM("qwen3:14b", provider="ollama"),
        mode="full",
    )
    ```

    <Tip>
      Full mode's fact extraction quality depends on your configured LLM. A larger, instruction-following model like `qwen3:14b` or `llama3.1:8b` will produce better-structured facts than a smaller one.
    </Tip>
  </Tab>
</Tabs>

## How retrieval works

When you call `mem.context()` or `mem.search()`, Smriti runs your query through all four retrieval channels in parallel and fuses the results using Reciprocal Rank Fusion (RRF):

| Channel | What it searches | Best for |
|---|---|---|
| **Lexical** (BM25 / FTS5) | Full-text keyword index over episodes and facts | Exact phrases, names, specific terms |
| **Semantic** (vector / numpy) | Cosine similarity against stored embeddings | Paraphrases, conceptual matches |
| **Entity** (graph traversal) | Hop through entity relationship links | "Who works with Rachel?", connections |
| **Temporal** | Date-anchored proximity scoring | "What happened in March?", before/after |

You can select individual channels or use named **retrieval profiles** (`facts`, `relations`, `timeline`, `deep`, `auto`) to shape each query independently — right down to which channels fire.
