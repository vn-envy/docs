Narad has two distinct systems that make it feel smarter the more you use it: **Smriti** (memory) and **Tapas** (self-learning). Smriti recalls relevant past conversations before every agent run so the Avatāras always have context. Tapas scores each response after the run, and promotes high-quality patterns as compressed learnings called **Sutras** — injected into future runs to compound over time. Both systems run entirely on your machine. No conversation, embedding, or learned pattern is ever sent to an external server.

## Smriti — Conversation Memory

Every time an Avatāra completes a run, Narad embeds both the task and the response using the Gemini `text-embedding-005` model (768 dimensions; OpenAI `text-embedding-3-small` is the fallback) and writes the vector to a local **LanceDB** store at `~/.narad/memory/`. It also writes to a **SQLite FTS5** full-text index at `~/.narad/memory_fts.db` for exact-match recall.

At the start of the next run, before the Avatāra sees your request, Narad calls `recall()`: it embeds your current task, runs an approximate nearest-neighbour search over LanceDB, applies the Vismriti decay filter, and prepends the surviving memories as a `[MEMORY]` block in the enriched task.

### How Memories Are Recalled

The recall pipeline runs these steps in order:

<Steps>
  <Step title="Embed the current task">
    Narad embeds your incoming message (the same model used for storage). The embedding is cached with `@lru_cache(128)` so repeated queries within a session do not trigger duplicate API calls.
  </Step>
  <Step title="Run approximate nearest-neighbour search">
    LanceDB finds the top-3 most semantically similar past conversations using L2 distance. Records with a distance greater than 1.3 are discarded as too dissimilar to be useful.
  </Step>
  <Step title="Apply Vismriti decay (90-day TTL)">
    Any memory older than 90 days is automatically excluded. This is the **Vismriti** (forgetting) layer — stale context is worse than no context.
  </Step>
  <Step title="Run FTS5 exact-match recall (Parashurama only)">
    For Parashurama, Narad also queries the FTS5 BM25 index for exact-match hits — code snippets, error messages, and URLs. This layer is skipped for other Avatāras.
  </Step>
  <Step title="Prepend the memory block">
    Surviving memories are prepended to the task as a structured `[MEMORY]` block. The Avatāra reads this context before it sees your message.
  </Step>
</Steps>

### Vismriti — Memory Decay

Memories expire after **90 days** by default. This prevents stale or outdated context from polluting future responses. The decay window is configurable via the `max_age_days` parameter if you need to adjust it.

A deduplication gate also runs on every new memory write: if the nearest existing memory has an L2 distance less than 0.10, the write is skipped — near-duplicate memories are not stored.

### Smriti v2 — Project-Scoped Wiki

For project-tagged sessions, Narad also maintains a per-project Markdown wiki at `~/.narad/wiki/{user_id}/{project_id}/`. The **Scribe** engine compiles a wiki entry after each session, capturing entities, decisions, and context. This wiki is injected as a `[PROJECT CONTEXT]` block — the outermost layer of enrichment, above sutras and conversation memory.

View your project wikis in the **Dashboard → Memory** tab.

### Memory Storage Layout

| Path | Contents |
|------|----------|
| `~/.narad/memory/` | LanceDB vector store — semantic embeddings of all task/response pairs |
| `~/.narad/memory_fts.db` | SQLite FTS5 full-text search index |
| `~/.narad/wiki/` | Per-project Markdown wiki pages (Smriti v2) |
| `~/.narad/sessions/` | Yantra JSONL session traces (one file per session) |

## Tapas — Self-Learning Engine

Tapas (Sanskrit: *disciplined austerity that generates transformative power*) runs asynchronously after every Avatāra response. It never blocks the reply you see — it works in the background. The goal is to identify high-quality responses and distil them into **Sutras**: compressed learned patterns that are injected into future runs of the same Avatāra.

### How Tapas Scores a Response

After each run, Tapas submits the task and response to a **DeepSeek R1 judge** (independent of the Avatāra being scored) with an Avatāra-specific rubric. The judge returns a score, a reason, and two hard boolean gates:

<Steps>
  <Step title="Domain-specific rubric scoring">
    The judge scores the response against an Avatāra-specific rubric. For Parashurama: penalises skeleton code and fixes without root-cause diagnosis. For Matsya: penalises uncited claims. Scores run from 0.0 to 1.0.
  </Step>
  <Step title="Hallucination hard gate">
    The judge returns `hallucination_free: true/false`. If `false`, the score is zeroed unconditionally and promotion is blocked. A `blocked_hallucination` event is written to the Karma log.
  </Step>
  <Step title="Sequence correctness penalty">
    The judge returns `sequence_correct: true/false`. If `false`, a −0.20 penalty is applied to the score (recoverable — not a hard zero).
  </Step>
  <Step title="Promotion threshold check">
    If the final score reaches **0.80** or above, the response advances to the CAI self-critique pass.
  </Step>
  <Step title="CAI self-critique (Constitutional AI)">
    A second LLM call asks three questions: Does this harm vulnerable users? Does this undermine user autonomy? Is this specific enough to be reusable? The response must pass all three to be promoted.
  </Step>
  <Step title="Sutra promotion">
    Sessions passing all gates are promoted as a **Sutra** — a compressed pattern stored in `~/.narad/config/sutras.jsonl` with a 90-day TTL.
  </Step>
</Steps>

### What Is a Sutra?

A Sutra (Sanskrit: *thread* — minimum representation of maximum wisdom) is a compressed learned pattern extracted from a high-scoring response. Sutras are ranked at injection time using `0.6 × tapas_score + 0.4 × keyword_overlap(task, sutra.query)`. Up to five sutras are injected per Avatāra per run as a `[LEARNED PATTERNS]` block.

Sutras pass through a lifecycle: `PENDING → ACTIVE → REVERTED`. You review and manage them in the **Dashboard → Sutras** tab.

<Note>
  Every Sutra promotion, revert, and expiry is recorded in the immutable **Karma audit log** at `~/.narad/config/karma.jsonl`. Each entry includes `triggered_by` (session ID), `tapas_score`, `content_hash` (SHA-256 of sutra text), and `critique_passed`. Call `GET /karma` to query the full audit trail, or open **Dashboard → Karma** in the UI.
</Note>

### Managing Sutras in the Dashboard

Open **Dashboard → Sutras** (the Tapasya tab) to see all Sutras grouped by status:

| Status | Meaning | Action available |
|--------|---------|-----------------|
| Pending | Scored ≥ 0.80, awaiting your review | Accept or revert |
| Active | Injected into matching future runs | Revert (with two-step confirmation) |
| Reverted | Permanently suppressed | View only |

Use **Accept all (N)** to bulk-accept pending Sutras. Reverting requires a two-step confirmation with a 4-second auto-cancel window to prevent accidental suppression.

### Tapas Safety Nets

- **Duplicate suppression** — a new Sutra candidate is checked against all active Sutras by batch cosine similarity. If any match exceeds 0.92 similarity, the candidate is dropped.
- **Injection sanitisation** — before any Sutra is injected into a prompt, `_sanitize_sutra()` strips candidates containing prompt injection patterns. Blocked Sutras are logged to Karma with action `blocked_injection`.
- **24-hour cooldown** — a newly promoted Sutra is not injected until 24 hours after promotion (configurable via `SUTRA_COOLDOWN_HOURS`).
- **Tapas skip event** — if the DeepSeek R1 judge is unreachable after two retries with exponential backoff, Tapas emits a `tapas_skipped` Karma event and the session continues without scoring. No response is ever blocked by a judge timeout.

### Tapas Configuration

| Environment variable | Default | Effect |
|---------------------|---------|--------|
| `TAPAS_JUDGE_MODEL` | `deepseek/deepseek-r1` | Override the judge model |
| `TAPAS_PROMOTE_THRESHOLD` | `0.80` | Minimum score for promotion |
| `TAPAS_SUTRA_TTL_DAYS` | `90` | Days before a Sutra expires |
| `TAPAS_SIM_THRESHOLD` | `0.92` | Cosine similarity threshold for dedup |
| `SUTRA_COOLDOWN_HOURS` | `24` | Hours before a new Sutra is injected |
| `SUTRA_MAX_ACTIVE` | `5` | Maximum Sutras injected per Avatāra per run |
